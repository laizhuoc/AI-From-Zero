# 推荐系统怎么做AB测试？线上指标有哪些？

> by @Laizhuocheng

---

## 一、简介：为什么推荐系统离不开AB测试？

想象你是一位厨师，研发了一道新菜品。在正式推出前，你会怎么做？直接换掉菜单上的所有菜？当然不会。你会让一部分顾客先试吃，收集反馈，确认真的好吃再全面推广。

推荐系统的AB测试，就是这个"试吃环节"的科学版本。

推荐算法每天都在迭代：今天优化了协同过滤，明天上线了深度学习模型，后天调整了排序权重。每个改动都可能影响千万用户。如果没有科学的验证方法，就像蒙着眼睛开车——可能撞大运，也可能翻车。

AB测试的本质是**控制变量实验**：把用户随机分成两组，一组用老策略（对照组），一组用新策略（实验组），在相同时间段内对比效果。这样得出的结论才有说服力。

---

## 二、什么是AB测试？

AB测试（A/B Testing），也叫分流测试或对照实验，是一种通过对比两个或多个版本的产品策略，来判断哪个效果更好的方法。

**说人话就是**：像做化学实验一样，保持其他条件不变，只改变一个变量，然后观察结果差异。

在推荐系统中，AB测试的核心是**流量分层**：
- 按用户维度做哈希分桶，保证同一用户始终进入相同实验组
- 避免用户一会儿看到新策略，一会儿看到老策略，导致体验混乱
- 分桶后对照组跑基线策略，实验组跑新策略
- 关键是控制单一变量，确保策略差异是唯一影响因素

## 三、AB测试如何工作？

### 3.1 流量分桶：让用户"各就各位"

推荐系统有"记忆性"——用户今天看到的内容会影响明天的推荐结果。如果按请求分桶，同一个用户一会儿看到旧策略，一会儿看到新策略，他的行为数据就被污染了。

**正确的做法是按用户ID哈希分桶**：

```java
public class ABTestBucket {
    private static final int BUCKET_COUNT = 100;
    
    public int getUserBucket(String userId) {
        int hashCode = userId.hashCode();
        // 避免负数，使用与运算转正
        int positiveHash = hashCode & 0x7FFFFFFF;
        return positiveHash % BUCKET_COUNT;
    }
    
    public boolean isInExperiment(String userId, int startBucket, int endBucket) {
        int bucket = getUserBucket(userId);
        return bucket >= startBucket && bucket <= endBucket;
    }
}
```

用`0x7FFFFFFF`做与运算是为了把负数哈希值转成正数。分桶范围设成0到99共100个桶，如果实验流量是10%，就让0到9号桶进实验组。这样同一个用户每次计算结果都一样，既保证了随机性，又保证了一致性。

### 3.2 实验流程：科学实验的四步走

AB测试本质上是在线的对照实验，整个过程就是科学实验的那套方法：

**第一步：提出假设**
- 明确实验目标：是想提升点击率还是转化率？
- 确定最小样本量：预期提升5%，需要多少流量才能检测出显著差异？

**第二步：设计实验**
- 确定分桶比例：通常实验组和对照组各占50%
- 设置实验周期：至少跑一周，观察指标稳定后再决策
- 做AA测试：两组跑相同策略，验证分流是否均匀

**第三步：收集数据**
- 实时采集用户行为数据
- 给每个数据打上实验标签（实验组/对照组）

**第四步：验证假设**
- 计算核心指标的差异
- 做统计显著性检验（p值<0.05认为显著）
- 分析细分人群表现，避免辛普森悖论

### 3.3 分层实验：多团队并行不冲突

大公司有多个团队同时跑实验，流量管理变得复杂。常见的做法是**分层实验**：

- 第一层：召回策略实验
- 第二层：排序算法实验  
- 第三层：UI展示实验

用户进来后，在每一层独立分桶。可能在第一层进了A组，第二层进了B组，第三层进了对照组。这样不同层的实验互不干扰，能同时进行更多实验。

**正交分流的秘诀**：用不同的哈希种子。第一层用`userId`做哈希，第二层用`userId + "layer2"`做哈希，第三层再换个字符串。这样同一个用户在不同层的分桶结果是独立的。

## 四、线上指标体系

### 4.1 三层指标体系

| 层次 | 指标类型 | 典型指标 | 特点 |
|------|---------|---------|------|
| **第一层** | 直接行为指标 | CTR、停留时长、完播率 | 敏感度高，快速反馈 |
| **第二层** | 业务转化指标 | CVR、GMV、加购率 | 归因周期长，商业价值 |
| **第三层** | 生态健康指标 | 多样性、新颖度、基尼系数 | 长期健康，防止过度优化 |

**第一层：直接行为指标**
- **点击率CTR**：点击次数/曝光次数，最基础的即时反馈指标
- **停留时长**：反映内容质量，用户是否真正感兴趣
- **完播率**：短视频场景下，播放完成度比点击率更能说明问题

**第二层：业务转化指标**
- **转化率CVR**：下单用户数/点击用户数，反映推荐内容和用户真实需求的匹配度
- **GMV**：成交总额，最终的商业目标
- **加购率**：用户加购行为，购买意愿的中间指标

**第三层：生态健康指标**
- **内容多样性**：防止算法只推爆款，损害长尾内容
- **新颖度**：新内容曝光比例，扶持创作者生态
- **基尼系数**：衡量流量分配均衡度，防止马太效应

### 4.2 指标冲突怎么办？

实际中经常遇到指标trade-off：
- 提升多样性可能导致短期CTR下降
- 推新品可能暂时降低转化率

**解决思路**：
1. 根据业务阶段权衡：增长期关注短期转化，成熟期重视用户体验
2. 设置组合指标：加权求和，或设置阈值（保证CTR不低于基线的前提下最大化多样性）
3. 长期追踪：保留部分实验流量，观察几周甚至几个月的长期走势

## 五、实际应用与常见陷阱

### 5.1 实际应用场景

| 实验类型 | 典型例子 | 关注指标 |
|---------|---------|---------|
| **算法迭代** | 协同过滤→深度学习 | 召回准确率、CTR |
| **界面改版** | 横滑→瀑布流 | 浏览深度、停留时长 |
| **策略调整** | 增加新品曝光权重 | 新品CTR、长期留存 |

### 5.2 常见陷阱与解决方案

**陷阱一：流量污染**
- **问题**：社交场景下用户会互相影响（比如A看到的内容分享给B）
- **解决**：做更粗粒度的分桶，比如按地域或设备分桶

**陷阱二：新奇效应**
- **问题**：新策略上线初期因为新鲜感指标虚高，一周后回落
- **解决**：拉长观察周期，至少跑1-2周，看指标是否稳定

**陷阱三：辛普森悖论**
- **问题**：整体提升但某些细分人群下降（比如高活用户提升5%，低活用户下降3%）
- **解决**：分人群分析，必要时做差异化策略

**陷阱四：位置偏差**
- **问题**：排在前面的商品天然获得更多点击
- **解决**：确保两组位置分配策略一致，或做位置归一化处理

### 5.3 决策标准

不能指标一提升就上线，也不能数据不好看就立刻放弃：

| 提升幅度 | 决策建议 |
|---------|---------|
| 核心指标>2%，无反向指标 | 直接上线 |
| 提升1%-2% | 结合成本评估 |
| 提升<1% | 效果不明显，暂不上线 |

**关键原则**：
- p值<0.05且持续稳定（不能只看某一天）
- 检查是否有反向指标恶化
- 评估工程成本（提升1%但需要三倍计算资源，可能不值得）

## 六、总结与思考

推荐系统的AB测试，表面是技术问题，本质是对**科学方法论**和**业务理解深度**的考验。

**核心要点回顾**：
1. **流量分桶**要按用户维度，保证一致性和随机性
2. **指标体系**分三层：行为指标、业务指标、生态指标
3. **实验设计**要控制单一变量，做AA测试验证分流
4. **效果评估**要看统计显著性，警惕新奇效应和辛普森悖论

**更深层的思考**：

AB测试只能告诉我们"新策略是否比老策略好"，但回答不了"什么才是最好的策略"。它是对已知选项的验证工具，而不是发现新大陆的探险船。

真正优秀的推荐工程师，不仅要知道怎么跑实验，更要知道**什么时候该做实验、该测什么、如何解读数据背后的故事**。数据是表象，用户价值才是本质。当你看到CTR提升了2%，要问的不是"怎么全量上线"，而是"用户真的更满意了吗"。

毕竟，算法的终极目标不是优化指标，而是创造价值。
