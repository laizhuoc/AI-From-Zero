# OpenClaw如何控制上下文不超过Context Window？

> by @Laizhuocheng

---

## 一、简介

想象你正在开会，桌上堆满了各种文件：会议议程（系统提示）、之前的会议记录（对话历史）、工具说明书（Skill定义）、参考资料（记忆文件）。你的桌面大小有限（Context Window），当文件太多时，你必须决定哪些放在手边、哪些收进抽屉、哪些直接扔掉。

这就是AI Agent面临的现实挑战。Context Window是LLM一次能"看到"的最大文本量，而在Agent场景下，它会被**系统提示、对话历史、Tool定义、Skill说明、记忆文件**同时争抢。当这些加起来超出上限，模型要么报错，要么开始"失忆"——忘记重要的上下文信息。

对于普通聊天，Context满了重开一个对话就好。但OpenClaw这样的Agent是持续运行的，有时一个任务本身就需要几十轮工具调用，你不能随便截断。这使得**Context管理成为Agent工程里最需要主动设计的问题之一**。

---

## 二、什么是Context Window管理？

Context Window管理是指在LLM的上下文容量限制下，通过智能的策略和机制，确保关键信息能够被模型访问到，同时避免超出限制导致的性能下降或错误。

**通俗理解**：就像管理一个有限大小的工作台，你需要决定哪些工具和材料放在手边（热数据），哪些收进抽屉（温数据），哪些存到仓库（冷数据）。关键是要保证当前任务所需的一切都能快速获取，同时不浪费空间。

---

## 三、Context Window管理如何工作

### 谁在吃掉你的Token？

Agent的Context和普通对话不一样，它要塞下更多东西：

**主要Token消耗来源**：

| 来源 | 典型token占用 | 增长特性 |
|------|--------------|---------|
| **系统Prompt/Soul** | 500-2000 | 相对固定 |
| **Skill列表** | 每个约24+ token | 随启用Skill数量线性增长 |
| **对话历史** | 无上限增长 | 随时间持续增长 |
| **工具调用记录** | 每次可达数千 | 随任务复杂度增长 |
| **记忆文件** | 按需注入 | 可控但需要策略 |

其中**增长最快、最难控制的是对话历史和工具调用记录**。一个长期运行的OpenClaw实例，历史记录可能积累几十万token，远超任何模型的Context Window。

### 核心解法：分级记忆系统

最根本的解法是**不把所有历史都放进Context**，而是建立分级记忆系统：

**1. 工作记忆（Working Memory）**
- **内容**：当前对话的近几轮，完整保留
- **作用**：模型理解"你现在说的是什么"必须的上下文
- **特点**：高优先级，完整保留，实时更新

**2. 摘要记忆（Summary Memory）**
- **内容**：把较早的对话压缩成摘要，存进MEMORY.md
- **示例**："用户偏好使用Python，项目在~/workspace/myapp，之前讨论过用FastAPI做后端"
- **优势**：摘要远比原始对话节省token，保留关键信息

**3. 语义记忆（Semantic Memory）**
- **内容**：把历史对话向量化存进向量数据库
- **使用方式**：只在相关时候检索，通过向量搜索找到相关片段注入Context
- **场景**：用户问"上次我们讨论的API设计"，精准定位相关内容

```
分级记忆架构
├── 热层（工作记忆）：当前对话上下文，完整保留
├── 温层（摘要记忆）：关键信息摘要，结构化存储
└── 冷层（语义记忆）：完整历史向量化，按需检索
```

### 具体工程手段

#### 1. Skill按需加载

OpenClaw允许通过`allowBundled`白名单控制哪些Skill进入系统Prompt。如果你的工作流只涉及GitHub和邮件，就没必要让天气、智能家居等几十个Skill白白占用token。

**实践建议**：
- 分析实际使用场景，只启用必要的Skill
- 定期审查Skill使用情况，禁用不常用的Skill
- 为不同场景配置不同的Skill白名单

#### 2. 历史窗口截断

最粗暴但常见的方案：只保留最近N轮对话，更早的直接丢弃。

**适用场景**：
- 任务相对独立，不需要很长历史
- 对话主题频繁切换
- 性能要求高于历史完整性

**缺点**：会真正丢失信息，不适合需要长期上下文的任务。

#### 3. 工具调用结果压缩

工具返回的原始数据往往很冗长（比如搜索结果返回10篇文章的全文）。在传给下一轮之前，先让LLM提炼关键信息，只把精炼后的摘要放进Context。

```javascript
// 工具调用结果压缩示例
const rawSearchResults = await searchTool(query);
const summarizedResults = await llm.summarize(rawSearchResults, {
  maxTokens: 200,
  focus: "key facts and actionable insights"
});
// 只将摘要传入下一轮Context
```

#### 4. 分模型路由

OpenClaw支持配置主模型和辅助模型：
- **复杂推理任务**：用Claude这类大上下文模型
- **简单任务**：用更便宜的小模型（Heartbeat检查、格式化任务）

既节省成本，也避免把宝贵的Context预算浪费在简单任务上。

## 四、Context Window管理的优缺点

| 优势 | 劣势 |
|------|------|
| **保证系统稳定性**：避免Context溢出导致的错误和性能下降 | **实现复杂度高**：需要设计完整的分级记忆架构 |
| **提升长期任务能力**：通过外部存储突破Context限制 | **响应延迟增加**：向量检索和摘要生成会增加处理时间 |
| **降低运行成本**：减少不必要的Token消耗 | **信息损失风险**：摘要和压缩可能导致关键细节丢失 |
| **灵活性高**：可以根据任务需求动态调整策略 | **调试困难**：多层记忆架构的问题难以定位 |
| **可扩展性强**：支持长时间运行的复杂任务 | **存储成本**：向量数据库和外部存储需要额外维护 |

## 五、Context Window管理的实际应用与发展趋势

### 实际应用场景

#### 1. 长期运行的Agent服务

**场景**：一个7*24小时运行的客服Agent，每天处理数百个对话。

**挑战**：对话历史不断积累，几天后就可能超出Context Window。

**解决方案**：
- 实时对话：保留最近10轮完整历史
- 会话摘要：每10轮生成一个摘要存入MEMORY.md
- 向量检索：当用户问及更早的内容时，从向量库检索相关片段

**效果**：
- **稳定性**：系统运行数周无溢出错误
- **效率**：90%的查询不需要外部检索
- **用户体验**：用户感觉Agent记住了所有对话

#### 2. 复杂项目协作

**场景**：Agent协助开发者完成一个持续数周的软件项目。

**挑战**：需要记住项目架构、技术选型、已解决的问题等大量信息。

**解决方案**：
- **工作记忆**：当前文件的代码和最近的修改
- **摘要记忆**：项目架构文档、关键技术决策
- **语义记忆**：完整的代码库、issue记录、讨论历史

**效果**：
- **代码理解**：Agent能够理解跨文件的代码关联
- **上下文感知**：根据项目特点提供针对性建议
- **知识沉淀**：项目结束后，所有知识可以导出复用

#### 3. 个性化服务

**场景**：个人助理Agent，了解用户的偏好、习惯和历史需求。

**挑战**：需要长期记住用户的个性化信息，但不能每次都加载全部历史。

**解决方案**：
- **用户画像**：将用户偏好提炼成结构化数据
- **偏好缓存**：高频使用的偏好放在热层
- **历史检索**：低频或细节信息通过向量检索获取

**效果**：
- **个性化**：提供符合用户习惯的建议
- **隐私保护**：敏感信息可以选择性加载
- **性能优化**：减少不必要的上下文传输

### 当前局限性

**技术挑战**：
- **信息提取精度**：摘要生成可能丢失关键细节
- **检索相关性**：向量检索的准确性影响上下文质量
- **实时性要求**：高频任务下，外部检索的延迟成为瓶颈

**实践挑战**：
- **配置复杂度**：不同场景需要不同的配置策略
- **调试困难**：多层记忆的问题难以定位和复现
- **成本控制**：向量数据库和外部存储需要持续投入

### 发展与演进

**优化方向**：

**智能压缩算法**：
开发更智能的对话摘要算法，不仅能提取关键信息，还能保留上下文的逻辑关系和情感色彩。比如使用图神经网络建模对话结构，生成更有语义的摘要。

**自适应窗口管理**：
系统能够根据任务复杂度和历史模式，自动调整Context窗口的大小和内容。简单任务用小窗口，复杂任务动态扩展。

**多模态记忆**：
不仅存储文本信息，还能存储图像、音频、视频等多模态数据的摘要和索引，支持更丰富的上下文理解。

**联邦记忆网络**：
多个Agent实例可以共享记忆库，但通过隐私保护技术确保用户数据安全。比如使用差分隐私或同态加密。

**未来展望**：

**神经符号系统**：
结合神经网络和符号推理，将对话历史转化为可查询的知识图谱，既保留语义理解能力，又支持精确检索。

**记忆增强学习**：
Agent能够从记忆使用模式中学习，优化自己的记忆策略。比如哪些信息应该记住，哪些可以遗忘，哪些需要详细记录。

**实时协同记忆**：
多个Agent可以实时共享和更新记忆，形成一个分布式的智能记忆网络，支持大规模协作任务。

**人机记忆融合**：
将人类的记忆方式和AI的记忆技术结合，创造更自然、更高效的记忆系统。比如支持联想记忆、情感记忆等人类特有的记忆模式。

## 六、总结与思考

Context Window的限制本质上是在提醒我们：**LLM的"注意力"是有限且宝贵的资源**，工程师的职责之一是替它管好注意力的分配。

人类也有工作记忆的限制——我们不可能同时记住所有事情，所以我们有笔记、有日历、有档案。Agent的记忆系统设计，在某种意义上是在为LLM建立一套"**外脑**"：

- **把不需要时时刻刻记住的信息卸载到外部存储**
- **需要的时候再精准取回来**

随着LLM Context Window的持续扩大（已从早期的4K增长到今天的百万级），这个问题的紧迫性在降低，但永远不会消失。因为Agent的记忆本身也会随使用时间不断增长，窗口再大也总会有被填满的一天。

**分级记忆不只是当下的工程应对，更是Agent系统的长期架构原则。**

这意味着优秀的Agent设计应该：
1. **主动管理Context使用**，而不是被动等待溢出
2. **建立智能的记忆分层机制**，平衡完整性和效率
3. **提供可配置的策略**，让用户根据需求调整
4. **保持透明性**，让用户知道哪些信息被保留、哪些被压缩

最终目标是让Agent既能处理复杂的长期任务，又不会因为Context溢出而"失忆"或"混乱"。

---

**总结**：Context Window管理通过分级记忆系统，将有限的上下文容量与无限的历史信息进行智能平衡。它不仅是技术实现，更是对注意力资源的精细化管理。

**思考**：真正的智能不仅在于能记住多少，更在于知道什么值得记住，什么可以遗忘。Context管理的精髓在于模拟人类的记忆智慧——保留精华，舍弃冗余，让每一次注意力都用在刀刃上。
