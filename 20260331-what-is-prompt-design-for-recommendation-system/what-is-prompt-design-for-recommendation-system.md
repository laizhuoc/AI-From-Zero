# 推荐系统的 Prompt 设计：如何把用户历史行为融入 Prompt？

## 一、简介

大模型开始进入推荐系统，但很多工程师遇到了同一个问题：给大模型一堆用户数据，它不一定能给出好的推荐。

原因往往不在于模型能力不足，而在于 **Prompt 设计没做好**。

推荐系统的 Prompt 设计，本质上是把非结构化的推荐任务转化为语言模型能理解的指令。同样一批用户数据，不同的 Prompt 组织方式，推荐效果可能天差地别。

这篇文章系统梳理推荐系统 Prompt 设计的核心方法，重点解决「怎么把用户历史行为优雅地融入 Prompt」这个关键问题。

---

## 二、什么是推荐系统的 Prompt 设计

用一个类比来理解：

> 你要让一个刚入职的新同事帮你推荐商品。
> 你可以说：「帮我推荐几个商品」——模糊，结果大概率不对。
> 也可以说：「我是 25 岁女生，最近在护肤和健身，上周买了兰蔻小黑瓶和 Nike 运动服，帮我推荐 5 个适合我的商品，用 JSON 格式输出」——清晰，结果大概率不错。

**Prompt 设计就是第二种做法的系统化。** 它需要回答三个问题：
1. 模型扮演什么角色？（系统定义）
2. 用户是什么样的人？（特征描述）
3. 我要什么样的推荐结果？（任务指令）

---

## 三、Prompt 五模块结构

一个完整的推荐 Prompt 应该包含以下五个模块：

| 编号 | 模块 | 作用 | 示例 |
|------|------|------|------|
| 01 | 系统角色 | 定义 AI 身份和能力边界 | 「你是一个了解用户深层需求的推荐专家」 |
| 02 | 任务定义 | 明确推荐目标 | 「发现新兴趣点」或「深挖已知偏好」 |
| 03 | 用户特征 | 融合用户画像和历史行为（核心） | 用户基础信息 + 行为序列 |
| 04 | 候选集范围 | 限定推荐池 | 具体商品列表或品类约束 |
| 05 | 输出格式 | 规范化输出 | `JSON 格式、指定字段、推荐理由` |

### 完整示例：电商场景 Prompt

```
你是个性化推荐助手。

用户画像：25-30 岁女性，关注美妆和健身
近期浏览：雅诗兰黛面霜（3次）、瑜伽垫、蛋白粉
购买记录：兰蔻小黑瓶、Nike 运动服
兴趣标签：护肤、健身、轻奢品牌

基于以上信息，推荐 5 个最适合该用户的商品，说明推荐理由。
输出 JSON 格式：{"items": [{"id": "", "name": "", "reason": ""}]}
```

这个 Prompt 的设计要点：
- 角色定位明确（推荐助手，而非通用助手）
- 用户特征分层呈现（画像、浏览、购买）
- 行为数据带了频次（面霜 3 次，说明复看意图强）
- 输出格式严格规定（方便下游系统解析）

## 四、用户历史行为融入的核心技巧

这是整个 Prompt 设计中最难的部分。用户历史行为可能有几百条，不可能全塞进去，如何筛选和组织是关键。

### 技巧一：时间加权

**近期行为权重更高。** 用户三天前看的商品，和今天刚看的商品，对当前推荐的参考价值差别很大。

实践方案：按时间段分层描述，最近 24 小时单独列出，最近一周简单汇总，更早的行为抽取标签即可。

### 技巧二：交互分层

**按交互深度分层处理，而不是平等对待所有行为。**

```
浏览（弱信号）< 收藏（中等信号）< 加购（强信号）< 购买（最强信号）
```

在 Prompt 中可以这样体现：
```
已确认购买：兰蔻小黑瓶、Nike 运动服
加购未付：雅诗兰黛面霜
最近浏览：瑜伽垫、蛋白粉、跑步机（各 1-2 次）
```

### 技巧三：模式提取

**提取行为模式，而非简单罗列商品列表。**

❌ 低效做法：`用户浏览过：商品A、商品B、商品C、商品D、商品E……`

✅ 高效做法：`用户偏好日系护肤品，对价格 200-500 元区间的精华类产品有明显兴趣`

模式描述比商品列表更精炼，Token 消耗更少，模型理解效果更好。

### 技巧四：Top-K 筛选

**行为太多时聚类或筛选，只保留最有代表性的。**

可以按品类聚合，每个品类取最近 2-3 个代表性行为；也可以按交互强度排序，优先保留购买和加购行为。

## 五、两种主要行为融入思路对比

| 思路 | 序列化文本 | 结构化模板 |
|------|-----------|-----------|
| **核心逻辑** | 按时间顺序排列行为 | 按交互类型分类呈现 |
| **优点** | 保留完整时序信息 | 压缩长度，结构清晰 |
| **缺点** | Token 消耗大 | 丢失时序细节 |
| **适用场景** | 行为数量少、时序重要的场景 | 行为数量多、需要压缩的场景 |

**序列化文本示例：**
```
用户昨天浏览了华为手机
前天搜索过无线耳机
上周购买了充电宝
```

**结构化模板示例：**
```
已确认对机器学习有学习需求
正在探索编程技能拓展
对前端开发保持关注
```

**最佳实践：混合策略**——重要行为（购买、高频浏览）保留明细，次要行为（低频浏览）做聚合，兼顾信息密度和 Token 效率。

## 六、工程落地：从数据到 Prompt 的完整链路

### 四步数据处理流程

```
用户行为数据
    ↓ 提取：根据场景有选择地取数，设置时间窗口
    ↓ 清洗：过滤噪声，剔除异常行为（如爬虫、误操作）
    ↓ 聚合：按品类/意图聚合，控制 Prompt 长度
    ↓ 组装：选择模板，生成最终 Prompt
```

### 代码示例（Java 伪代码）

```java
public String buildRecommendationPrompt(User user, UserBehavior behavior) {
    String template;
    
    if (behavior.getTotalActions() < 10) {
        // 冷启动用户模板：行为少，用人口统计学兜底
        template = "你是推荐助手。用户是%s，%d岁，请推荐适合的商品...";
    } else {
        // 个性化用户模板：提取行为特征
        String behaviorText = aggregateBehaviorToText(behavior);
        template = "你是懂用户的推荐专家。\n\n用户画像：%s，%d岁\n%s\n...";
    }
    
    return String.format(template, user.getGender(), user.getAge(), behaviorText);
}
```

关键设计：**冷启动用户和活跃用户走不同模板**，避免行为稀少时 Prompt 信息量不足导致推荐效果差。

### 成本控制三层优化

| 层级 | 方案 | 效果 |
|------|------|------|
| 第一层 | **缓存机制**：用户行为未更新时直接复用上次结果 | 减少 50%+ 的重复调用 |
| 第二层 | **批处理**：合并多个用户请求，降低 API 调用次数 | 降低 API 成本 |
| 第三层 | **Prompt 压缩**：用缩写代替完整描述 | Token 数减少 1/3 |

## 七、高频追问与应对策略

**Q：怎么证明 Prompt 设计比传统推荐更好？**

设计分层指标体系：短期看 CTR/CVR 变化，中期观察用户留存率，长期追踪推荐品类分布均衡性（避免信息茧房）。

**Q：用户刚产生新行为，怎么快速更新 Prompt？**

准实时策略：行为缓冲池 + 分级更新频率。购买行为立即生效，浏览行为延迟聚合（5 分钟一批），避免频繁更新造成的资源浪费。

**Q：新用户没有历史数据怎么办？**

冷启动退化策略：利用注册时填写的基本信息 + 同类用户群体的行为模式 + 引导式交互快速收集偏好（如「请选择你感兴趣的品类」）。

**Q：什么场景不适合用 LLM 做推荐？**

高并发低延迟场景（延迟要求 < 50ms）、用户行为稳定规律的工具类应用（直接用协同过滤就够）。这些场景用混合架构更合适：传统模型负责高频请求，LLM 负责复杂意图理解。

## 八、总结与思考

推荐系统的 Prompt 设计，核心是两件事：

1. **结构化**：用三段式（系统角色 + 用户特征 + 任务指令）把推荐任务组织清楚
2. **抽象化**：行为数据要提取模式，而不是机械罗列，时间加权 + 交互分层 + Top-K 筛选是三大核心技巧

值得深思的是：**Prompt 设计是工程约束与自然语言灵活性的平衡**。太结构化会丢失语义灵活性，太自由会让模型失去方向。找到这个平衡点，需要通过 AB 测试不断验证，而不是靠直觉拍脑袋。

大模型在推荐系统中的价值，最终要用业务指标来衡量——不是「模型看起来理解了用户」，而是「用户真的点了、买了、留下来了」。
